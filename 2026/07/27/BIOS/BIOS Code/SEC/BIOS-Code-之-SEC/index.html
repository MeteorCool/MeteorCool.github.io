如下图，BIOS，或者说UEFI 的简略启动流程说明，第一个阶段就算SEC，计算机系统上电或重启后进入这个阶段。

SEC 需要做什么？

1：接受并处理系统启动和重启信号及异常信号；

2：CAR（Cache as RAM）系统运行在SEC阶段时，仅CPU和CPU内部资源被初始化，各种外部设备和内存都还没被初始化，因而需要一些临时RAM区域，用于代码和数据的存取。

3：作为可信系统的根：SEC阶段为安全验证阶段，作为取得系统控制权的第一部分，SEC阶段是整个可信任系统的根。SEC阶段能被系统信任，是其后各个阶段被信任的基础。通常，SEC把控制权交给PEI阶段前，可以验证PEI阶段。

4：传递系统参数给PEI阶段：系统当前状态、可启动固件（Boot Firmware Volume，BFV）的地址和大小、临时RAM区域的地址和大小、栈的地址和大小。

当系统启动，CPU的指针指向0xf:0xffe0的实模式地址并开始执行该地址下的代码。代码首先通过Boot Firmware Volume(BFV)的唯一标识找到它的基地址，进而找到SecCore的入口函数 _ModuleEntryPoint()，然后将控制交给 _ModuleEntryPoint().

注意1：EDK2可以在Ovmfpkg文件夹找到sec，ovmfpkg全称是Open Virtual Machine Firmware Package，是 EDK2 专为QEMU/KVM 虚拟化虚拟机开发的 UEFI 固件平台包，只用来存放和虚拟硬件强绑定的源码、编译配置、虚拟化专属驱动，编译生成ovmf.fd

注意2：因为Ovmf是仅针对QEMU 虚拟机的包，如果你是使用Intel/AMD 等硬件平台，不管是AMI 还是insyde来说，他们编译都是针对对应的硬件组PCH，也就是PlatformPkg，Sec 相关代码也会因为硬件厂商的封装在对应的pkg文件夹当中，与EDK2是不一样的，这里只是基于EDK2 code对SEC 代码流程进行分析

注意3：由于EDK2 的ovmf 包是基于虚拟机QEMU进行运行，是默认CPU处于64位模式下，但是对于硬件启动来说，CPU 是从16位模式切换到32位保护模式，再到64位模式的流程，这部分的代码流程逻辑需要区分。

调用前面的C 函数

SecCoreStartupWithStack是 SEC 汇编与 C 的桥梁，在无 DRAM 的 CAR 环境下校验固件、管理缓存内存、完成平台早期初始化、检索 PEI 内核，打包硬件信息通过 HOB 交给 PEI，最终结束 SEC 阶段。EDK2版本会额外增加 TD 虚拟机安全校验、VCPU 信息管理、RTMR 可信测量。

基于AMI/Insyde Code，该函数命名有所不同，对于非intel FSP，一般AMI 命名为SecStartup，反之一般则是FspSecStartup

insyde则是SecMain和H2OFspSecMain，不同的硬件或者Code版本可能会有所不同~

几个关键变量的说明：

1.输入参数EFI_FIRMWARE_VOLUME_HEADER：BIOS flash被分为若干个FV，每个FV 都有其首地址，存放位置就是这个FV header，这个header内定义的变量也都是为寻找FV，校验FV 等相关动作服务的。

2.EFI_SEC_PEI_HAND_OFF，由名字可以大概理解这个数据结构体的功能，用来SEC 到PEI 的数据传递，也是UEFI 规范内唯一合法传递逻辑，传递的信息包括car，栈，FV，CPU 等信息

3.SEC_IDT_TABLE

SEC_IDT_TABLE，顾名思义，中断描述表，其中只有俩变量，第一个是pei service的指针，实际在SEC是没有该服务存在的，这儿的定义可以理解为提前占位，后续SEC 完成将控制全交给pei 阶段后，该指针就是pei service 的handle。

第二个变量，如果你同时研究EDK2和IBV BIOS代码会发现，EDK2 和IBV 定义是有所区别的，EDK2 定义的是256个全中断描述表，而IBV的Code当中仅有34个，两者的区别还是因为硬件差异，EDK 基于虚拟机，也就是默认CPU 处于64位模式，相关资源都已经就绪，但实际主板正常开机显然不是这样，这时候没有内存，只有cache，而且SEC本身也不需要处理PCH 外设等设备中断，只需要处理CPU 34个内部中断即可，也就是我们看到的CLI（清除中断标志指令） 操作（屏蔽外部中断）。
