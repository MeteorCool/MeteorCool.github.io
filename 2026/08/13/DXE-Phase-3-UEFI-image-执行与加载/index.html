UEFI Image加载与执行

Image是指一类包含可执行代码的文件。UEFI 规范规定，UEFI image采用微软公司定义的PE32+可执行文件格式。PE32+与 PE32 的区别在于前者支持 64 位代码。

PE 和 COFF 文件格式规范专门为 UEFI 执行环境定义了四种 Subsystem

EDK2 核心代码里面只有前三种，可能是还没更新，或者是EDK2基于虚拟机环境是不需要用上的

这些 subsystem 决定了 UEFI image的类型，也决定了image加载到什么类型的内存中去，以及image的入口函数退出时系统采取的动作

当 UEFI Application image退出时，系统总是将它卸载并释放它占用的内存。当 UEFI Boot Service或 Runtime Service 驱动image退出时，只有当退出时的返回值为一个 UEFI 错误码时，系统才会将它卸载并释放内存，否则image会常驻内存。

UEFI image通过 LoadImage() Boot Service 加载到内存中。 LoadImage() Boot Service 中有一个PE32+ 装载器，它将 PE 中的所有节(Section)都装入内存。然后，对内存中的代码根据加载的实际地址进行重定位。StartImage() Boot Service 根据 UEFI 规范为每一种支持的 CPU 架构定义的调用约定(Calling Convention)将控制权转交给一个在内存中已经装载好的 UEFI image的入口地址。

可执行image服务初始化

CoreInitializeImageServices()函数

调用时机：DXE 内核刚从 PEI 阶段交接完成、进入 DXE 初始化早期最先执行的镜像服务初始化函数。

核心职责：

  1. 遍历 HOB 链表，搜寻 PEI 阶段传递过来的 DXE‑Core 内存分配 HOB
  2. 从 HOB 取出 DXE 内核镜像基址、大小、入口函数
  3. 初始化 DXE‑Core 自身的 LOADED_IMAGE_PRIVATE_DATA（加载镜像私有结构体）
  4. 为 DXE 内核安装 EFI_LOADED_IMAGE_PROTOCOL
  5. 初始化 PE‑COFF 镜像模拟器协议的监听事件、回调、链表
  6. 对 DXE‑Core 内存区域执行 UEFI 镜像内存保护

遍历 HOB List，寻找描述 DXE Foundation image的 Memory Allocation HOB。DXE IPL 将 DXE Foundation image加载到内存后，会为之创建 Memory Allocation HOB 来描述 DXE Foundation在内存的起始地址和长度。

循环遍历 HOB 链表，查找 DXE‑Core 的模块内存 HOB

从 HOB 提取 DXE 内核镜像关键信息

  1. MemoryBaseAddress：DXE‑Core 镜像加载到内存的物理起始地址；
  2. MemoryLength：整个 PE‑COFF 镜像占用内存字节大小；
  3. EntryPoint：PEI 获取到的 DXE‑Core 入口函数；
  4. gDxeCoreFileName：全局变量保存 DXE 内核模块 GUID（充当文件名标识）

注意：UEFI 当中 FFS 模块可以使用 GUID 充当文件名标识。

安装 EFI_LOADED_IMAGE_PROTOCOL 协议

创建 PE‑COFF 模拟器协议的通知事件

注册协议通知监听，CoreRegisterProtocolNotify：DXE 内核协议服务函数，订阅指定 GUID 协议；只要系统里任何驱动安装了 EdkiiPeCoffImageEmulatorProtocol，就 Signal 触发前面创建好的事件，执行 PeCoffEmuProtocolNotify 回调。

初始化可用模拟器双向链表头以及UEFI 镜像内存保护。

可执行image加载

CoreLoadImage() 函数

CoreLoadImage() 是 DXE‑Core 对外暴露的镜像加载顶层入口，对应 UEFI 规范 EFI_BOOT_SERVICES.LoadImage() 底层实现。

  • 作用：从固件卷 FFS、磁盘文件、内存缓冲读取 PE‑COFF 镜像、执行重定位、导入符号修复、分配镜像私有结构体、安装 EFI_LOADED_IMAGE_PROTOCOL。

EDK‑II 性能调试宏，记录该镜像加载开始时间戳；入参暂时为空，加载成功之后回填句柄。 可在固件性能日志中查看每个驱动加载耗时。

  1. BootPolicy：透传启动策略标记

  2. ParentImageHandle：父镜像句柄透传

  3. FilePath：文件设备路径

  4. SourceBuffer：内存源缓冲

  5. SourceSize：缓冲大小

  6. 指定镜像加载到固定地址；NULL = 交由内核自动分配内存，绝大多数驱动都是动态分配

  7. NULL：输出参数，返回加载之后镜像物理地址，上层不需要接收所以传 NULL

  8. ImageHandle：输出镜像句柄，透传出去

  9. NULL：不需要返回 LOADED_IMAGE_PRIVATE_DATA 私有指针

  10. PE 镜像加载属性标志位（重点）

结束计时，绑定当前镜像句柄，性能日志可以区分是哪一个驱动镜像的加载耗时。

CoreLoadImageCommon函数

EDK‑II DXE‑Core PE‑COFF 镜像加载最底层通用主函数

参数合法性校验、获取父镜像信息

区分加载来源：内存缓冲 / FV 固件卷 / 文件系统 / LoadFile (2) 协议

根据设备路径读取 PE‑COFF 镜像至内存缓冲区

调用 Security / Security2 架构协议执行镜像验签、安全校验

分配 LOADED_IMAGE_PRIVATE_DATA 镜像私有管理结构体

安装 EFI_LOADED_IMAGE_PROTOCOL、LoadedImageDevicePath、HiiPackageList 等协议

调用 CoreLoadPeImage 执行 PE‑COFF 解析、内存分配、节区拷贝、重定位、导入表修复

调试镜像信息注册、运行时镜像 CFI 安全标记、镜像内存权限保护

资源回收、失败时卸载镜像、返回镜像句柄

TPL 断言：镜像加载只能够在低于 TPL_NOTIFY 的优先级运行，高优先级禁止文件 IO 与内存分配；

CoreLoadedImageInfo() 根据镜像句柄反向取出 LOADED_IMAGE_PRIVATE_DATA；

父句柄必须是合法已经加载完毕的镜像句柄。

条件1：

当调用方已经把 PE 镜像读到内存，加载器直接复用该缓冲区；

仅尝试解析设备路径得到所属设备句柄；缓冲区长度为 0 直接返回加载错误。

条件2

文件路径为空直接找不到文件。后面按优先级依次尝试定位设备协议

查找优先级：FirmwareVolume2 → SimpleFileSystem → LoadFile2 → LoadFile

EFI_FIRMWARE_VOLUME2_PROTOCOL：优先搜索固件卷，DXE 驱动基本全部存放于 FV；

EFI_SIMPLE_FILE_SYSTEM_PROTOCOL：磁盘分区文件系统；

LoadFile2 / LoadFile：底层设备加载协议，用于无文件系统设备加载镜像。

FHand.FreeBuffer=TRUE：代表镜像缓冲区由堆分配，加载流程结束必须释放；

LoadFile 协议设备路径会发生改变，因此拼接生成更新后的完整设备路径。

UEFI 镜像安全校验（Security2 / Security 架构协议）

UEFI 固件安全启动流程就在此处执行镜像验签、证书校验、平台安全策略检查

  1. Security2（新版）：完整镜像验签、证书链校验、安全启动策略；
  2. Security（旧版）：读取 FV‑FFS 头部预先保存好的认证状态；

FV 里面的 FFS 文件在 PEI 阶段就已经标记 AuthenticationStatus 认证标志位。

EFI_SECURITY_VIOLATION：签名校验失败，上层 CoreDispatcher 会标记驱动 Untrusted，后续可重试加载；

EFI_ACCESS_DENIED：平台安全策略永久禁止加载镜像；

其余安全错误直接终止加载流程。

该结构体就是该镜像在内核当中的管理对象，包含 LoadedImage 协议、入口地址、内存页信息、HII 资源、镜像上下文等。

设备句柄自带设备路径，剥离设备节点，只保留后面的文件路径节点

安装 LoadedImage 协议，暂时关闭协议通知回调

最后入参 FALSE：禁止触发协议通知事件；

原因：此时 PE 镜像还没有加载完成，等到 PE 加载完毕之后再重新安装协议触发通知。

  1. 读取 PE 头、节表
  2. 分配 EfiBootServicesCode / EfiRuntimeServicesCode 类型内存
  3. 拷贝 .text/.data/.rdata 各个 Section
  4. 执行基址重定位
  5. 修复导入表 IAT
  6. 收集 HII 资源、调试信息、DllCharacteristicsEx 属性

当传入固定地址 DstBuffer 空间不足，返回 EFI_BUFFER_TOO_SMALL，向外输出需要的内存页数。

内核维护全局调试镜像链表；调试工具能够遍历所有已经加载镜像、获取符号与 PE 信息。

如果运行时代码段镜像不支持 CFI 着陆垫，则全局标记关闭内存属性表 CFI 兼容；

针对 Windows 运行时镜像安全防护。

前面安装协议的时候关闭通知；现在 PE 镜像加载完毕，重装接口触发所有注册了 LoadedImage 协议监听的回调函数。

该协议保存完整原始设备路径，区别于 LoadedImage‑>FilePath（仅文件子路径）。

HII 负责固件 UI、字符串、窗体、字体资源。PE 镜像内 HII 资源段地址保存在 ImageContext。

UEFI 镜像内存权限保护

CoreUnloadAndCloseImage 失败回收动作

  1. 卸载句柄上面所有已经安装协议
  2. 释放镜像堆内存、设备路径副本
  3. 释放 LOADED_IMAGE_PRIVATE_DATA

可执行image执行

CoreStartImage() 函数

执行已经通过 CoreLoadImage 加载完毕的 PE‑COFF 镜像入口函数 DriverEntry。

它负责镜像上下文切换、长跳转缓冲区准备、调用镜像入口、驱动执行完毕后的上下文还原、句柄数据库扫描、应用程序自动卸载、返回退出数据。

CoreLoadedImageInfo() 通过镜像句柄反向查找 LOADED_IMAGE_PRIVATE_DATA；

镜像私有结构体不存在、镜像已经标记 Started＝正在运行 → 参数非法；

如果上一步 LoadImage 加载镜像失败，直接返回加载失败状态码，禁止启动损坏镜像。

Image->Machine 取自 PE 头 Machine 字段，代表镜像架构（X64 / ARM64）；

两种可以运行镜像的条件

  1. 原生架构匹配，CPU 原生支持；
  2. 架构不匹配，但存在 PeCoffEmu PE‑COFF 模拟器，可以仿真异种架构镜像；

都不满足则返回 EFI_UNSUPPORTED，不可以启动。

异种架构镜像（例如 ARM64 固件运行 X86‑64 驱动），需要把镜像内存地址、入口点交给模拟器管理；注册失败直接终止启动。

  1. CoreGetHandleDatabaseKey()：抓取当前句柄数据库版本快照 Key；驱动运行结束后对比快照，检测驱动新建、修改过哪些协议句柄；
  2. mCurrentImage：DXE‑Core 全局变量，标记此刻正在执行的镜像；嵌套调用 StartImage 时形成调用栈；
  3. 保存当前任务优先级 TPL 到镜像私有数据，驱动返回之后必须恢复原有 TPL。

​ UEFI 驱动调用 Exit () 退出时，内核依靠 mCurrentImage 判断是哪一个镜像发起退出。

分配 long‑jump 跳转缓冲区，用于镜像 Exit () 函数

UEFI 驱动入口执行过程中可以调用 BS->Exit() 结束自身镜像；

Exit 内部调用 LongJump 跳回到 CoreStartImage 函数，不通过函数 return 正常返回。

  1. 分配跳转栈缓冲区，额外增加对齐余量；

  2. ALIGN_POINTER

    将 JumpContext 调整至架构要求的缓冲区对齐地址；

    x64、ARM64 对 setjmp 缓冲区都有硬性内存对齐约束。

RegisterMemoryProfileImage：内存性能剖析，标记当前镜像内存归属；

Image->Started = TRUE 标记镜像正在运行，禁止重复 StartImage；

调用镜像入口函数 EFI_STATUS DriverEntry(EFI_HANDLE ImageHandle, EFI_SYSTEM_TABLE *SystemTable)

UEFI 规范规定驱动入口不允许直接 return；

如果驱动入口函数 return，内核主动调用 CoreExit 执行镜像退出流程，触发 LongJump 跳转回到 SetJump。

驱动在运行期间有可能修改任务优先级 TPL；镜像退出之后内核强制恢复到镜像启动之前的 TPL，防止 TPL 泄露引发后续内核异常。

释放 setjmp 缓冲区堆内存。

调试打印退出信息；

如果上层调用者传入 ExitData 指针，则把驱动 Exit 产生的宽字符串缓冲区传出给调用方；

调用方不接收退出数据，内核直接释放 ExitData 堆内存。

保存镜像返回状态，判断是否卸载镜像

卸载规则：

  1. 驱动入口返回失败代码 → 卸载该驱动镜像；
  2. EFI‑APPLICATION 类型固件应用程序，运行结束之后一律自动卸载；
  3. 正常成功返回的 Boot‑Time Driver 驱动则常驻内存，不会卸载。
整体运行流程时序
  1. 参数校验，确认镜像加载成功、尚未启动；
  2. 检查 PE 镜像架构，原生运行或者启用 PE‑COFF 模拟器；
  3. 抓取句柄数据库快照，切换全局 mCurrentImage 镜像上下文；
  4. 分配对齐的 SetJump 跳转缓冲区；
  5. SetJump 锚定跳转点；
  6. 调用镜像 DriverEntry 入口；
    • 分支 A：驱动正常 return → 内核调用 CoreExit → LongJump
    • 分支 B：驱动内部直接调用 Exit () → LongJump
  7. 跳转回到 SetJump 位置，恢复 TPL 优先级；
  8. 释放跳转缓冲区、还原父镜像上下文；
  9. 驱动触发新增设备句柄，则执行 ConnectController 绑定驱动；
  10. 处理 Exit 退出字符串；
  11. 根据规则卸载应用程序 / 失败驱动；
  12. 结束性能计时，返回驱动执行状态

可执行image退出

CoreExit() 函数

CoreExit()函数实现了 Exit() Boot Service。

把 TPL 提升到 TPL_NOTIFY。

目的：防止重入、防止并发。Exit 操作修改镜像全局状态，提升 TPL 屏蔽其他事件回调打断流程。

根据句柄拿到镜像私有结构体，句柄非法直接跳 Done 恢复 TPL 返回错误。

镜像还没有被 StartImage 启动，但调用了 Exit。

这种情况不做 LongJump，直接卸载镜像所有资源，返回成功。

属于异常边界场景：加载完镜像，没 StartImage，直接调用 Exit。

只有当前正在运行的镜像（全局 mCurrentImage）才允许调用 Exit ()。

不允许 A 镜像调用 Exit 去终止 B 镜像。

这就是为什么需要全局变量 mCurrentImage，它标记此刻哪个镜像拥有 Exit 权限。

如果调用者传入退出字符串 ExitData：

  1. 在 DXE 堆上新分配一块内存；
  2. 把用户传入的 ExitData 拷贝进来；

为什么拷贝？驱动栈上的内存当 LongJump 之后栈会被销毁，不能直接持有调用方栈指针。

这块内存后续由 CoreStartImage 负责释放或者返回给上层调用者。

  1. 恢复 TPL 到原来级别；
  2. LongJump，跳转到 Image->JumpContext，也就是 CoreStartImage 里面 SetJump() 的位置，传入返回值 -1。

​ 此时执行流直接回到 CoreStartImage：

LongJump 正常情况下永不返回。

如果代码跑到这里，说明底层库 LongJump 实现异常，触发 ASSERT。

最后：异常路径统一出口：恢复 TPL，返回错误码。

可执行image卸载

CoreUnloadImage () 函数

CoreUnloadImage 是 UEFI Boot Services UnloadImage() 的 DXE‑Core 内核实现。

UEFI 规范：

  • 如果镜像尚未启动：直接回收镜像全部资源。
  • 如果镜像已经启动运行过：调用镜像自身注册的 Unload() 回调函数；只有 Unload 返回成功，才会真正销毁镜像。
  • 真正的资源释放逻辑不在本函数，封装在内部函数 CoreUnloadAndCloseImage()。

CoreLoadedImageInfo() 根据句柄反向取出镜像私有结构体。句柄不是合法镜像句柄，返回 EFI_INVALID_PARAMETER。

if：镜像已经被 StartImage 启动过 Image->Started = TRUE

  1. 默认状态置为 EFI_UNSUPPORTED，代表不支持卸载；

  2. 检查

    函数指针：

    • 如果驱动实现了 Unload 回调：调用驱动提供的 Unload(ImageHandle)；把返回值赋给 Status；
    • 如果 Unload 指针为 NULL，Status 保持 EFI_UNSUPPORTED。

重点：已经运行过的镜像，内核不会直接回收资源。

UEFI 规范：驱动自己的协议、句柄、分配内存，必须由驱动的 Unload 函数主动释放。内核只负责 PE 镜像本身内存的释放。

else：镜像没有启动过 Started = FALSE

镜像仅调用 LoadImage，没有调用 StartImage。

直接置 Status = EFI_SUCCESS，不需要调用任何驱动回调，可以直接销毁

只有 Status 成功：

  • 要么镜像从未运行；
  • 要么镜像运行过，但驱动的 Unload() 回调返回成功；

才会调用内部函数 CoreUnloadAndCloseImage(Image, TRUE)，做真正销毁：释放 PE 镜像内存、卸载句柄上所有协议、释放私有结构体、设备路径副本等。

​ 如果 Unload() 返回失败，不会执行镜像销毁，镜像继续驻留内存。
