mPeiLoadImagePpi 专门负责从 FV（固件卷）读出 PEIM 的 PE‑COFF 文件、解析、分配内存、拷贝段、执行重定位、安全校验，输出模块运行地址与程序入口；它就是 PEI 阶段的 PE 镜像加载器。

PeiLoadImageLoadImageWrapper 是 EFI_PEI_LOAD_FILE_PPI 的外壳包装函数（Wrapper 跳板），它本身没有镜像加载业务逻辑，只负责参数透传、拿到 PeiServices 之后调用真正的加载主体 PeiLoadImageLoadImage()。

从 FFS‑FileHandle 取出 TE/PE32 可执行段 → 加载、内存拷贝、重定位 → 校验 CPU 架构 → 输出镜像基址、入口、安全状态、打印调试日志。

根据 Pcd 配置决定优先查找 TE 段还是 PE32 段

TE：压缩后的 EFI 可执行镜像，体积更小，Flash 节省空间

PE32：标准未压缩 PE‑COFF 镜像

Pcd 平台可配置加载器优先检索顺序。

PeiServicesFfsFindSectionData3() 作用：

  1. 根据 FileHandle 定位 Flash 上 FFS 文件
  2. 查找指定类型 Section
  3. 返回该段原始二进制指针 Pe32Data
  4. 回填镜像安全校验状态 AuthenticationState

如果优先查找的段找不到，则尝试第二种可执行段：

一个 FFS 文件内部必须含有 TE / PE32 其中一种可执行段，否则不能作为 PEIM。

  1. 判断当前阶段是 CAR (Cache‑as‑RAM) 还是 DRAM 已经初始化完毕；
  2. 从对应内存池分配运行时内存；
  3. 解析 PE 头、各个 Section（.text/.data/.reloc）；
  4. 将 Flash 中的原始段拷贝至新分配的内存；
  5. 处理 BaseRelocation 重定位表，修正代码内绝对地址；
  6. 解析 PE 导出表查找固定入口函数 PeimInitialize；
  7. 返回加载基址、内存大小、入口地址。

加载失败直接向上返回错误码：

重置 Pe32Data 指针指向内存中已经加载完成的镜像，注意：原先 Pe32Data 指向 Flash 原始镜像；现在指向 DRAM/CAR 当中已经重定位完成的运行副本，后续用来读取 PE 头、PDB 信息。

读取 PE 镜像机器类型，校验平台是否支持该架构

解析 PE 镜像内部 PDB 调试路径，获取模块文件名，EDK II 生成 efi 镜像的时候会把 pdb 调试文件路径写入 PE 符号区；加载器借此拿到模块名字打印到日志。

for循环：将文件的后缀名.pdb 变更为efi。

结合前面的dispatcher 流程，完整的调用路径如下：

GetPeCoffImageFixLoadingAssignedAddress

该函数属于 PE‑COFF 加载器内部接口，用于开启固定地址加载功能之后，从 PE 非代码段头读取编译阶段预置的定点加载地址、计算最终运行地址、校验并占用指定内存区间，实现 PEIM/DXE 模块加载到开发者预先指定的固定物理地址。

获取 PE 头指针、计算段头数组偏移

PE‑COFF 头部排布顺序：PE‑Signature(4字节) → EFI_IMAGE_FILE_HEADER → OptionalHeader → Section‑Header 数组

公式算出全部可选头结束之后，段头数组起始偏移 SectionHeaderOffset。

通过加载上下文的 ImageRead 回调，从 Flash 原始镜像读出当前段头；

ImageRead 是抽象读取接口，TE 压缩镜像、普通 PE32 镜像会绑定不同读取函数。

读取失败、读取长度不足段头大小 → 直接返回找不到定点加载地址；

重置 Status 标记。

Build 工具把 64‑bit 加载地址，低 32 位存入 PointerToRelocations、高 32 位存入 PointerToLineNumbers；

ReadUnaligned64 组合成完整 64 位地址。

Pcd < 0：相对偏移模式

  • ImageContext‑>ImageAddress 存放编译给出的偏移量
  • 最终加载地址 = DxeCodeTopAddress + 偏移
  • DxeCodeTopAddress 是固定加载区域的内存顶部基址

Pcd ≥0：绝对物理地址模式

  • ImageContext->ImageAddress 直接赋值为 ValueInSectionHeader（外层代码完成赋值

定点加载存在硬性约束：多个模块不能加载到重叠内存；

CheckAndMarkFixLoadingMemoryUsageBitMap 维护一张内存占用位图；

检查目标地址区间是否空闲；空闲就标记为已占用；地址冲突返回错误；

入参长度 = 镜像大小 + 段对齐，保证对齐之后完整内存区间被检查。

整体流程如下图：

CheckAndMarkFixLoadingMemoryUsageBitMap 核查输入的内存空间是否可用

定点内存分为两块：

  1. RuntimeCodePageNumber：运行时常驻代码页（退出 BootService 之后依旧保留）

  2. BootTimeCodePageNumber：仅启动阶段使用的临时定点代码页

    两者相加得到定点区域总页数。

宏 EFI_PAGES_TO_SIZE(PageCount)：页数 × 4KB (一页大小)，换算成字节总数。

DxeCodeTopAddress = 定点区域最高地址

定点区起始地址 = 顶部地址 − 定点区域总大小

1 个 UINT64 具备 64 bit，可以标记 64 个内存页的占用状态

bit = 0 → 页面空闲；bit = 1 → 页面已经被定点模块占用

(总页数 / 64)+1 向上取整，计算需要多少个 UINT64 数组元素

AllocateZeroPool 初始全部清零，所有页面默认空闲

gLoadFixedAddressCodeMemoryReady：全局标记，定点内存区域是否已经准备就绪

位图分配失败直接返回 EFI_NOT_FOUND，定点加载不可用

模块结束地址不能超过定点区顶部 DxeCodeTopAddress

模块起始地址不能小于定点区起始 DxeCodeBase

只要模块有一部分超出定点内存池，拒绝定点加载。

换算成相对于定点区起始的页偏移

EFI_SIZE_TO_PAGES(ByteLength)：字节大小 ÷ 4KB，转为页编号

  • BaseOffsetPageNumber：模块第一页在定点位图内的索引
  • TopOffsetPageNumber：模块占用区间之后第一个空闲页索引
  • 循环区间 [BaseOffsetPageNumber, TopOffsetPageNumber)

第一轮遍历：检查所有需要的页面是否空闲

Index / 64 → 定位到 UINT64 数组下标

Index % 64 → 当前页在 64 位变量里面对应的 bit 位

LShiftU64 (1, n) 生成掩码，测试对应比特位

如果任意一页 bit 等于 1，说明页面已经被别的定点模块占用，加载失败。

第二轮遍历，置位标记页面已占用,通过按位或，把对应内存页的比特置 1，完成占用标记；后续定点加载不能再分配该页。
