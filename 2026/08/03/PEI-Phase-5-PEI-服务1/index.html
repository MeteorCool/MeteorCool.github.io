PEI service 提供了PEI 几乎常用的功能，根据功能不同分为PPI、启动模式、HOB、FV数据空间、内存管理、状态码、系统重启、基本的I/O接口及扩展服务，服务定义如下：

（1）PeiInstallPpi，实现在 Ppi\Ppi.c，安装 PPI 服务列表到 PPI 数据库，不同的 PPI 由GUID 唯一标识。

和早期EDK2 版本有差异，通过静态函数 InternalPeiInstallPpi 重构，三个输入参数分别是：

PeiServices PEIM 对外拿到的标准PeiServicesTablePointer

PpiList：

关键宏Flags：

EFI_PEI_PPI_DESCRIPTOR_PPI：标记这条是有效 PPI，必须置位

EFI_PEI_PPI_DESCRIPTOR_NOTIFY_CALLBACK：这是 Notify，不是 PPI

EFI_PEI_PPI_DESCRIPTOR_TERMINATE_LIST：链表结束标记

Single：

FALSE：标准模式，外部 API PeiInstallPpi() 使用，遍历多条 PPI 链表，直到遇到 TERMINATE_LIST 标志

TRUE：PEICore 内部调用，只安装单个 PPI 描述符，不需要判断结束标记（给 ReinstallPpi、内部动态注册使用）

PrivateData = PEI_CORE_INSTANCE_FROM_PS_THIS (PeiServices);

通过PeiServices 指针反向找到PEICORE（peicore 的第一个成员就是peiservices）

后面则根据拿到的PEICORE 获取相关信息：

PpiListPointer 拿到全局 PPI 数据库管理头；

Index：下一条 PPI 要写入的数组下标；

LastCount = Index 重点！记录本次安装开始前的数量

For循环：遍历整条PPI描述符链表，无退出条件，通过内部break指令退出。

第一个判断条件，判断当前的PPI 是否合法，不合法则将当前数据库中的数据恢复到最后一次正确执行的状态并返回

PEI 全局PPI 在堆上是动态分配内存，当内存不足时，重新扩容，先申请更大的内存（PPI_GROWTH_STEP倍数），复制内容到新内存，修改指针。

将合法 PPI 描述符指针存入全局数组，下标自增，有效计数 + 1。

if 条件：

Single == TRUE：只处理当前这一条，直接 break；

Single == FALSE（外部标准调用）：判断当前描述符是否带有结束标记 TERMINATE_LIST，遇到标记停止循环；

不满足退出条件：PpiList++ 移动到数组下一个描述符，继续循环。

注意：PEIM 定义多条 PPI 时，最后一条结构体必须添加 EFI_PEI_PPI_DESCRIPTOR_TERMINATE_LIST，否则内存越界遍历

循环完成、所有 PPI 成功写入数据库后，调用 ProcessNotify()，callback 函数。

（2）PeiReInstallPpi 替换数据库内已经存在的一条 PPI

第一个判断条件，新旧PPI不能为空，否则无效，第二个判断条件判断新的PPI 必须合法，和install 安装新的PPI 检查逻辑一致

遍历整个PPI 数组，查找旧的PPI 是否存在，不存在则返回找不到，和install 不同的是，install 的动作是直接在数据尾部新增变量，但reinstall 是需要找到旧的PPI精准地址进行更换

新的PPI指针覆盖旧的。

最后执行的notify则是执行同步 Notify 回调。输入变量index，index+1则是单独指向被替换的PPI。

（3）PeiLocatePpi 在 PEI 全局 PPI 数据库中，根据 GUID 查找指定序号的 PPI 实例，我们在调用PPI之前都必须找到相对应的实例，一般是通过这个函数实现

for 循环：

从头到尾线性遍历全部已注册 PPI；

TempPtr 取出数组里保存的 EFI_PEI_PPI_DESCRIPTOR*；

CheckGuid 拿到该 PPI 描述符对应的 GUID。

（4）PeiNotifyPpi 注册PPI callback，向 PEI Core 注册一组 Notify 监听：当将来某个 PPI 通过 InstallPpi / ReinstallPpi 安装成功时，自动触发你注册的 NotifyFunction。

整体流程图

代码实现：

代码架构逻辑和install差不多，通过single 变量确定单独还是批量调用PPI。

定义了两组不同的数组PEI_CALLBACK_NOTIFY_LIST 和 PEI_DISPATCH_NOTIFY_LIST，NOTIFY_CALLBACK 存入 CallbackNotifyList

NOTIFY_DISPATCH存入 DispatchNotifyList，后续触发逻辑完全隔离。

经典容器反向寻址，获取 PEI 全局上下文，访问两套 Notify 全局数组。

for 循环无限循环通过break 指令退出，遍历整条NotifyList数组。

Notify 描述符 Flags 必须至少带有 NOTIFY_CALLBACK / NOTIFY_DISPATCH 二者其一。

校验失败：事务回滚，恢复两套 Notify 数组有效计数，直接返回错误。

后面则是notify的扩容动作，和install 的逻辑一致，扩容完成则重新更新内存和指针。

循环退出逻辑，和 InstallPpi 完全对称：

  1. Single=TRUE：仅单条，直接退出；
  2. Single=FALSE：判断是否遇到链表结束标记；
  3. 未满足退出条件，指针自增访问下一条 Notify 描述符。

注册后调用notify，当PPI 调用notifyPPI 时，如果目标PPI 已经安装完成，不会等到后面installPPI，会立刻触发本次callback。

对比 InstallPpi 内部的 ProcessNotify：

InternalPeiInstallPpi PPI 新增完成，扫描所有旧 Notify，匹配新增的 PPI；

InternalPeiNotifyPpi Notify 新增完成，扫描所有旧 PPI，匹配新增的 Notify；

二者互补，保证无论「先装 PPI 还是先注册 Notify」，回调都能正常触发。
